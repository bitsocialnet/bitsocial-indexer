# Web UI agent workflow

The React application is in `webui/`. Run its commands there using npm and the committed `package-lock.json`. Use `npm ci` after dependency changes and `npm run perf:install` once to provision the runner's browser.

## Automatic React verification

Run `npm run agent:verify` after relevant React changes. It runs the pinned React Doctor check, type checking, `perf:check` (which includes the collector compatibility/regression self-test before the deterministic application scenarios), and a normal production build. Do not run `perf:test` separately before `perf:check`; use it only when investigating the compatibility harness in isolation. CI runs the same checks and uploads `.react-perf` evidence, including on failures. Doctor inspects source patterns; it does not measure runtime performance or replace the runtime checks. Fix findings introduced by your change and report existing relevant findings without chasing an aggregate score.

CI sets `PERF_BASE` to the pull request base or previous push commit, omitting an empty/all-zero base. Set `PERF_BASE` explicitly when comparing against a known task base; a base resolved to `HEAD` uses a full scan. Run `npm run doctor:check` for the automated source check alone; `npm run doctor` remains the full advisory audit. Run `npm run perf:check` for three samples at 4× CPU slowdown, or `npm run perf:record -- --scenario populated-navigation --cpu 1 --samples 1` to capture a bounded investigation. The shared runner owns an isolated browser through the repository's `scripts/pw-session.sh` machine-wide lock and cleans up its browser, app server, and fixture API. Do not overlap another browser or heavy check. Use `--target webui`, `--scenario`, `--cpu`, `--samples`, or `--output` to scope runs. Keep generated reports and traces out of Git.

## Runtime evidence and scope

`webui/instrumentation-client.ts` synchronously installs pinned Bippy before hydration in development and explicitly enabled profiling builds. `window.__REACT_PERF__` provides `reset()` and `snapshot()` for bounded observations, plus instance/commit IDs and dropped-event accounting. `PerfBoundary` records official React Profiler subtree timings. Missing instrumentation, dropped events, or missing required timing coverage are failures, never a successful zero. Counts describe committed client renders; they do not count abandoned work or establish wasted work. Subtree timings are inclusive and must not be summed with descendant timings.

The checked-in scenarios use a local Node fixture API via `INDEXER_API`, fixed posts/replies, and observable content assertions. They cover populated home → community/board → thread navigation and native search submission. The 5archive variant also covers its reply permalink effect. No interactive pagination or local React settings controls exist in these apps. Most product components execute on the server: browser evidence covers client hydration/router transitions and the client subtree, not Server Component execution. Search submits a native form and changes documents; its snapshot covers the new document only. The compatibility harness verifies state/prop/context updates, memo bailouts, mounts/remounts, distinct instances, and a deliberate redundant-update regression. It runs the same development fixture suite against installed React and both Next-bundled renderer variants (canary and experimental), since App Router can use a different React version from `webui/package.json`. Each variant reports the expected React version and actual observed renderer versions; an unresolved variant or version mismatch fails the check instead of being skipped. Repeat this compatibility check after React, Next, or Bippy upgrades. These fixture results establish collector behavior for the tested renderer variants; they do not substitute for the real application scenarios or a separate production profiling capture.

Default scenarios use isolated development output in `.next-perf-dev`; their count and timing budgets describe that instrumented environment. The initial per-phase limits are deliberately generous and scenario-specific, not production service targets. Inspect each sample, the action readiness condition, and native trace before changing a budget. Record before/after evidence with identical build mode, data, CPU setting, and interaction. Do not weaken a budget merely to hide a regression.

## Separate production profiling

`npm run build:profile` builds `.next-perf` with Next's `reactProductionProfiling` and `NEXT_PUBLIC_REACT_PERF=1`. `npm run start:profile -- --port 3100` serves it. Normal `npm run build`/`npm start` continue using `.next` and exclude the collector and Profiler wrapper; never deploy `.next-perf` as the ordinary production artifact.

For deterministic profiling against an existing server, first run `node scripts/react-perf/fixture-api.mjs` in an owned terminal and use its printed `INDEXER_API` value for both `build:profile` and `start:profile`. Then run `npm run perf:record -- --url http://127.0.0.1:3100 --scenario populated-navigation`. An existing server must already use the same fixture contract. The runner does not stop an externally supplied server; stop only the server and fixture terminal you own afterward. A normal production preview can measure page performance but lacks the collector/React timing evidence required by these checks.

## Visual feedback

Agentation remains available in ordinary development through `webui/components/DevTools.tsx`, with server rendering disabled. The explicit profiling flag suppresses it in scenario and profiling builds so the toolbar cannot affect measurements. Use its toolbar to annotate elements and copy structured feedback into the coding conversation. The clipboard workflow does not require an MCP server. Keep all annotation and profiling tooling excluded from normal production bundles.

## Retrospectives

After a bug fix or substantive review correction exposes a preventable mistake, use the [retro skill](.agents/skills/retro/SKILL.md) to consider the smallest lasting prevention. Routine successful edits do not need a retrospective; no additional check is a valid outcome. Keep review-only requests free of edits.

## Optional Jev browser checks

`scripts/jev/README.md` documents an opt-in bounded browser helper using the installed Playwright CLI and existing machine-wide session lock. Supply the fixture-backed web UI URL, an explicit allowed-action plan, and deterministic completion assertions. Offline plan validation needs no credentials; live semantic choices require explicit `--live`, a pinned model, and a budget. Helpers automatically discover credentials and the default model from the private machine config described in that README, with environment overrides; `node scripts/jev/config.mjs --check` checks readiness without network calls. Offline validation does not read the config or key file. Keep generated evidence outside Git. Use existing deterministic scenarios for fixed navigation/search and Bippy for performance; model judgments do not replace those checks.
